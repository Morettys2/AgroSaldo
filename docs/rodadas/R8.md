## 2. O que mudou (e por quê)

### 1. Arquivos grandes quebrados

| Antes | Depois |
|---|---|
| `AppNavegacao.kt` (668 linhas) | `AppNavegacao` (a moldura: Scaffold, barras, bloqueio) + `Navegador` (as regras de navegar) + `GrafosDeNavegacao` (um grafo por área: conta, financeiro, clima) + `BarraInferior` |
| `LancamentoFormScreen.kt` (907) | `LancamentoFormScreen` + `TopoDoLancamento` + `CamposDoLancamento` + `TecladoNumerico` + `LancamentoFormAcoes` |
| `LancamentoListaScreen.kt` (676) | `LancamentoListaScreen` + `CabecalhoDaLista` + `FiltrosDaLista` |
| `InicioScreen.kt` (645) | `InicioScreen` + `CartoesDoInicio` |
| `ClimaScreen.kt` (489) | `ClimaScreen` + `CartoesDoClima` |

Hoje nenhum arquivo de tela passa de ~500 linhas.

O `Navegador` é o que eu mais gosto. Antes, a mesma proteção ("não empilhar duas telas iguais com toque duplo", "não dar voltar duas vezes") estava copiada em cada destino. Agora é uma função com nome:

```kotlin
navegador.abrir(Rotas.CONTA)                     // com launchSingleTop
navegador.fecharSeNoTopo(Rotas.FORM_PROPRIEDADE) // só volta se ainda estiver nela
navegador.irParaAba(Rotas.CLIMA)                 // sem perder o estado das abas
```

👉 **Lição:** arquivo grande não é problema por si só. O problema é **não achar as coisas**. Quebre por **responsabilidade**: a moldura, as regras, os destinos.

### 2. `LancamentoFormAcoes`: de 15 lambdas para 1 objeto

```kotlin
// antes
LancamentoFormScreen(uiState, titulo, aoFechar = {}, aoMudarTipo = {}, aoMudarCategoria = {}, … 15 vezes)

// depois
LancamentoFormScreen(uiState, titulo, acoes = LancamentoFormAcoes(aoSalvar = { salvou = true }))
```

Cada ação tem o padrão "não faz nada", então o preview e o teste preenchem só o que interessa. A classe é `@Immutable`, e o Compose não recompõe a tela à toa.

### 3. Formatação e análise estática

| Ferramenta | O que faz | Comando |
|---|---|---|
| **ktlint** + regras de Compose | confere a formatação e boas práticas de Compose | `./gradlew ktlintCheck` (o `ktlintFormat` arruma sozinho) |
| **detekt** | caça código complicado, duplicado ou perigoso | `./gradlew detekt` |
| **Android Lint** | erro quebra o build (`abortOnError = true`) | `./gradlew lintDebug` |

- As regras do ktlint ficam no **`.editorconfig`** da raiz, no estilo "Android Studio": é o mesmo do `Ctrl + Alt + L`.
- As do detekt ficam em `config/detekt/detekt.yml`.

O ktlint arrumou sozinho a formatação de 110 arquivos (espaços, quebras, ordem de import). Os achados que ele não arruma sozinho eu corrigi à mão, e eram bons:

- **`rememberUpdatedState`** nos `LaunchedEffect` que chamavam um callback (`aoConcluir`, `aoFocar`…) em 6 telas. Sem isso, se a tela recompõe com um callback novo durante o efeito, o efeito chama a versão **velha**. É um bug sutil clássico de Compose.
- **Propriedades privadas com `_`** (`_voltas`, `_falha`…) sem a pública correspondente ganharam nome de verdade (`voltasATela`, `ultimaFalha`). A convenção do Kotlin: `_x` só existe quando há um `x` público expondo.
- `AppNavegacao` ganhou o parâmetro `modifier`, como todo composable que desenha algo.
- Saíram os arquivos de exemplo do template (`ExampleUnitTest`, `ExampleInstrumentedTest`).

O detekt ficou com um **baseline** (`app/detekt-baseline.xml`): os achados antigos ficam registrados, e o CI só cobra **código novo**. Quando você mexer num arquivo, vale limpar os achados dele e regenerar com `./gradlew detektBaseline`.

👉 **Lição:** formatação não é assunto para revisão de código. A máquina confere, e a revisão fica para o que importa.

### 4. Testes de tela no JVM — Robolectric

Até a R7, os testes testavam a **regra** (ViewModel e domínio), mas não a **tela**. Agora `app/src/test/…/ui/TelasTest.kt` desenha a tela de verdade no JVM, sem emulador, e clica nela:

- digitar "1", "2", "5" no teclado mostra **R$ 1,25**, e "Apagar" volta para R$ 0,12;
- o botão **Salvar** fica desligado enquanto grava;
- formulário e Início sem propriedade levam ao cadastro;
- erro na primeira leitura aparece no Início, no lugar do convite ao cadastro;
- lista vazia por causa do filtro oferece "Limpar filtros".

O **Robolectric** simula o Android dentro do JVM. Rodam junto com os outros: `./gradlew testDebugUnitTest`.

### 5. Capturas de tela automáticas — Roborazzi

`CapturasDeTelaTest` desenha as 10 telas principais com os **ViewModels de verdade** sobre os dados de exemplo e salva PNGs em `app/build/capturas/`:

- Início claro, escuro e vazio;
- Lançamentos;
- Novo lançamento, também com fonte 2x;
- Clima, Histórico, Sítios e Login.

O CI publica as imagens na branch **`ci/capturas`**: dá para ver o visual de qualquer PR **sem abrir o emulador**, só abrindo a branch no GitHub. As fotos do README saíram de lá.

### 6. Testes do Worker e das preferências

- **Worker do aviso de chuva:** o trabalho saiu de dentro do `doWork()` para a função `verificarChuva(...)`, que recebe tudo de fora. O teste confere:
  - que notifica quando vai chover;
  - que respeita a permissão;
  - que pede *retry* sem internet ou com o serviço fora do ar;
  - que **desiste depois de 3 tentativas**.
- **Preferências (Robolectric):** "reiniciar o app" é criar uma instância nova da classe sobre o mesmo arquivo. O teste confere que sobrevivem:
  - **o contador de senhas erradas**;
  - a sessão;
  - o bloqueio por digital;
  - o olho.

## 3. O que testar no celular

Esta rodada não muda comportamento. Uma volta rápida já basta:

- [ ] Abrir o app, entrar, trocar de aba e voltar: o estado de cada aba continua.
- [ ] Toque duplo rápido em "Conta" ou "Histórico" abre **uma** tela só.
- [ ] Salvar um lançamento fecha o formulário; excluir mostra "Desfazer".
- [ ] Notificação de exemplo (Ajustes do aviso, build debug) abre o Clima.

No Android Studio, vale rodar uma vez:

```
./gradlew ktlintCheck detekt testDebugUnitTest
```
