# AgroSaldo — Roadmap

O app está **pronto para uso**: a versão 1.5 roda no celular do produtor, com o CI verde e 606 testes. Daqui pra frente o caminho tem quatro etapas: arrumar o que ficou pendente, proteger os dados do produtor, publicar na Play Store e, só se fizer sentido, crescer para a nuvem.

*Atualizado em 27/10/2026. Os prazos são estimativas de esforço, não datas marcadas.*

## 4. Etapa 2 — Dados do produtor seguros

Hoje, se o celular for perdido sem o backup do Android ligado, **os dados se perdem**. Esta etapa resolve isso sem precisar de servidor.

- [ ] **Exportar os dados** para um arquivo (CSV para abrir no Excel, ou JSON). O arquivo sai pelo compartilhar do Android: WhatsApp, e-mail ou Drive.
  - Resolve dois problemas de uma vez: é o **backup manual** do produtor e atende a **portabilidade da LGPD** (art. 18, V), o único direito do titular que ainda falta.
- [ ] **Importar** esse mesmo arquivo num celular novo, com conferência para não duplicar lançamentos. Os ids são UUID, então dá para detectar o que já existe.
- [x] **Migração 4 do banco** (feita em 02/11/2026, branch `feat/migracao-4-dono-obrigatorio`):
  - deixar `propriedades.usuario_id` obrigatório;
  - remover o `adotarPropriedadesSemDono`, que só servia para os dados de exemplo antigos;
  - seguir a regra da casa: subir a versão, escrever a migração, exportar o schema e criar o teste de migração.
- [ ] **Avisar o produtor** dentro do app quando o backup do Android estiver desligado. É uma sugestão a validar com ele.

## 5. Etapa 3 — Play Store (R9)

Abrir a branch `rodada/r9-play-store` a partir da `prod`.

### Privacidade e permissões

- [ ] **Política de privacidade num link público** (GitHub Pages). Ela precisa ter:
  - o nome do responsável e um e-mail de contato;
  - o IP que a Open-Meteo recebe;
  - como apagar os dados;
  - como funciona o backup.
- [ ] **Publicar a política de privacidade num repositório público separado** (ex.: `agrosaldo-privacidade`), porque o histórico deste repositório tem dados pessoais antigos; não tornar este repositório público sem antes limpar o histórico.
- [ ] Trocar `ACCESS_FINE_LOCATION` por **`ACCESS_COARSE_LOCATION`** e arredondar as coordenadas enviadas para 0,02°.
- [ ] Formulário **Data safety** da Play Console: localização, dados criptografados em trânsito e nada compartilhado além da Open-Meteo.

### Build de release

- [ ] Gerar **AAB** (`bundleRelease`) em vez de APK.
- [ ] **Play App Signing:** a chave atual (`C:\chaves\agrosaldo.jks`) vira só a *upload key*. **Nunca gerar uma chave nova:** com outra chave, o app não atualiza por cima do que o produtor já tem.
- [ ] Senhas da chave em `~/.gradle/gradle.properties`, **fora do repositório**.
- [ ] Ligar o **R8** (encolher e ofuscar o código) e testar o build de release inteiro, porque o R8 pode quebrar o Room ou o Hilt se faltar alguma regra. O R8 já está ligado e o `assembleRelease` compila (conferido em 28/10/2026); falta abrir o build de release no aparelho.
- [ ] `localeFilters += "pt-rBR"` para o pacote levar só o português.

### Play Console

- [ ] Declaração de recursos financeiros ("não oferece serviços financeiros"), público adulto e classificação indicativa.
- [ ] **Conta pessoal nova:** o Google exige um **teste fechado com 12 testadores por 14 dias seguidos** antes de liberar a produção. Juntar os testadores (turma, família, outros produtores) antes de começar. Conte umas **3 semanas** só para essa fase.

### Desejável nessa etapa

- [ ] Mover os textos para **`strings.xml`**, que permite traduzir no futuro. Hoje eles estão no código, e o `TextosComuns.kt` já prevê essa mudança.

## 6. Etapa 4 — Melhorias de produto

**São ideias, não decisões.** Cada uma precisa ser conversada com o produtor antes de entrar no código. O app é dele, e o uso real decide o que vale a pena.

| Ideia | Por que pode valer | Custo |
| --- | --- | --- |
| Relatório do mês ou do ano em PDF | Levar ao contador ou ao banco num pedido de crédito | Médio |
| Categorias personalizadas | Gastos que não cabem nas categorias atuais | Médio (mexe no banco) |
| Lançamentos que se repetem todo mês | Energia, arrendamento e salário entram sempre | Médio |
| Comparar safras e anos lado a lado | Ver se o ano foi melhor que o anterior | Médio |
| Widget na tela inicial com saldo e chuva | Ver sem abrir o app | Médio |
| Mais dados do clima (vento, umidade) | Ajuda a decidir a pulverização | Pequeno (a Open-Meteo já oferece) |

## 7. Etapa 5 — Futuro: nuvem e sincronização

**Hoje está fora do escopo** (decisão de out/2026). Só faz sentido se o app tiver mais usuários ou se o produtor quiser usar em mais de um aparelho.

- API própria (NestJS) com banco relacional, HTTPS e autenticação por token.
- Sincronização **offline-first**: o celular continua gravando no Room e sincroniza quando tiver sinal. Os ids UUID e o `atualizado_em` já preparam isso.
- **"Esqueci minha senha"** por e-mail, que só é possível com servidor.
- Uso em vários aparelhos e compartilhamento com a família ou o contador.
- **LGPD com servidor:** controlador e encarregado definidos, contrato com o provedor de nuvem, registro das operações e plano para incidentes.
- **Criptografia do banco local** (SQLCipher), se o tipo de dado ou de usuário passar a exigir.

## 9. Como tocar cada item

1. **Uma branch por item**, a partir da `prod` (`fix/...`, `feat/...`, `rodada/r9-play-store`).
2. **Plano antes de codar:** quais arquivos mudam e por quê.
3. **Teste junto:** regra nova ganha teste, e bug corrigido ganha um teste que falharia antes.
4. **PR com o CI verde.** O merge só acontece depois de testar no celular.
5. **Atualizar a documentação no mesmo PR:** a seção da `DOCUMENTACAO_TECNICA.mdx`, o `CLAUDE.md` se mudar uma regra ou decisão, e este roadmap (marcar o item como feito).
