# AgroSaldo — R6: regra no domínio e DI de verdade 🧱

Rodada de **arquitetura**. O seu pai não vê quase nada de diferente: a conta continua a mesma, só que agora mora no lugar certo. A única mudança visível é que **o app não vem mais com dados de exemplo**.

É também a rodada que mais rende argumento para a professora: MVVM "de livro", com regra de negócio testada sem Android e injeção de dependência explicada.

---

## 1. Como pegar esta rodada

Ela está na branch `rodada/r6-dominio`, com um **PR aberto** no GitHub.

1. No VS Code: `git fetch` e depois `git checkout rodada/r6-dominio`.
2. No Android Studio: **Sync** e **Build → Rebuild Project**.
3. Rode os testes instrumentados (`app/src/androidTest`, botão direito → Run). Eles mexem no banco de verdade e a nuvem não roda eles.
4. Tudo certo? **Merge do PR** no GitHub.

> ✅ Desta vez **o app inteiro foi compilado de verdade**, telas Compose inclusive. Criei um GitHub Actions que roda `testDebugUnitTest assembleDebug lintDebug` em todo push. O ✔️ verde no PR quer dizer que compilou, que todos os testes passaram e que o lint não reclamou.

### ⚠️ Os dados de exemplo no seu celular

O banco **já criado** no seu celular continua com a "Fazenda São João da Serra" e o "Sítio Boa Vista" de exemplo: a mudança só vale para banco novo. Para começar do zero:

**Configurações → Apps → AgroSaldo → Armazenamento → Limpar armazenamento.**

O celular do seu pai **não muda nada**: o APK de release nunca teve dado de exemplo.

## 2. O que mudou (e por quê)

### 1. A conta do dinheiro mora no domínio — `domain/financeiro/ResumoFinanceiro.kt`

A mesma conta, "receitas − despesas do mês da propriedade", estava escrita de **4 jeitos** em 4 ViewModels:

| Onde | Como fazia |
|---|---|
| `InicioViewModel` | `filter` por tipo + `sumOf` |
| `LancamentoListaViewModel` | `valorComSinal` + `ehReceita` |
| `HistoricoViewModel` | `ehReceita` / `!ehReceita` |
| `PropriedadeListaViewModel` | `valorComSinal` |

Agora existe um lugar só:

- `totais(lancamentos)` devolve um `TotaisDoPeriodo`, com receitas, despesas, saldo e a proporção da barra;
- `resumoDoMes(lancamentos, propriedadeId, mes)` faz o recorte do mês;
- `rankingDeGastos(lancamentos, quantos)` monta o top 3 do Início e o top 5 do Histórico;
- `propriedadeAtual(lista, id)` resolve "a selecionada ou, se ela sumiu, a primeira", que também estava repetido em 4 telas.

São **funções puras**: entra lista, sai número. Sem banco, sem Android, sem coroutine. O `ResumoFinanceiroTest` testa tudo em milissegundos: centavos, mês, outra propriedade, empate no ranking…

👉 **Lição:** o ViewModel **junta** os dados (Flow do banco, seleção, mês) e o domínio **calcula**. Se amanhã a regra mudar (por exemplo, "não contar lançamento agendado no saldo"), muda num arquivo só, e o teste diz se quebrou algo. No NestJS seria tirar a regra do controller e pôr num service puro.

### 2. `SelecaoAtual` deixou de ser global

Antes era um `object`: qualquer arquivo podia fazer `SelecaoAtual.selecionar(...)`. Isso trazia dois problemas.

- **Dependência escondida.** Olhando o construtor do `LancamentoFormViewModel`, não dava para saber que ele mexia na seleção das outras telas.
- **Testes frágeis.** Como o estado sobrevivia entre um teste e outro, todo teste precisava de `SelecaoAtual.limpar()` no `@Before`. Bastava esquecer um para outro teste falhar "do nada".

Agora é uma `class`. Existe **uma** instância no app, criada no container, e cada ViewModel recebe a sua no construtor (`selecao: SelecaoAtual`). Nos testes, cada classe de teste cria a própria `SelecaoAtual()`.

👉 **Lição:** estado compartilhado não é a mesma coisa que estado global. "Compartilhado" quer dizer que todos recebem **a mesma instância**; "global" quer dizer que qualquer um pega a instância sozinho. O primeiro dá para testar; o segundo, não.

### 3. `Repositorios` virou `Dependencias` — DI manual de livro

| Antes | Depois |
|---|---|
| `object Repositorios` em `data/` | `class Dependencias` em `di/` |
| `Repositorios.inicializar(context)` chamado no App **e** no Worker | o `AgroSaldoApp` cria a instância: `val dependencias by lazy { Dependencias(this) }` |
| Factory lia `Repositorios.lancamentos` | Factory lê `dependencias.lancamentos`, que vem do `APPLICATION_KEY` |
| `AppNavegacao(desfazer = Repositorios.desfazer)` como parâmetro padrão | a `MainActivity` passa o `desfazer` explicitamente |

Como uma `Factory` acha o container:

```kotlin
val Factory = viewModelFactory {
    initializer {
        // "dependencias" = (this[APPLICATION_KEY] as AgroSaldoApp).dependencias
        InicioViewModel(
            selecao = dependencias.selecao,
            lancamentoRepository = dependencias.lancamentos,
            // ...
        )
    }
}
```

É exatamente o padrão do guia oficial "Manual dependency injection" do Android. Por que não Hilt?

- O Hilt **gera este mesmo código** por anotação. Para aprender, é melhor ver a fiação.
- O Hilt traz kapt/KSP, plugin e anotações em todas as classes, e o app nem é grande.
- Se um dia precisar, a troca é mecânica: as classes já recebem tudo pelo construtor.

👉 **Lição (frase para a professora):** "Os ViewModels não sabem de onde vêm as dependências; recebem tudo pelo construtor. Um único container, guardado pela `Application`, cria cada objeto uma vez e faz a ligação. Isso é injeção de dependência manual."

### 4. Código de teste saiu do APK — `src/testFixtures`

Os 9 fakes `*Memoria` (repositórios e preferências em memória), o `DadosDeExemplo` e o `Semeador` estavam em `src/main`, ou seja, **dentro do APK do seu pai**, sem servir para nada lá.

Agora estão em `app/src/testFixtures/`, um *source set* que o Gradle compartilha com os testes unitários (`src/test`) e com os instrumentados (`src/androidTest`) e que **não entra no APK**. No `build.gradle.kts`:

```kotlin
testFixtures { enable = true }
```

👉 **Lição:** `src/main` é o que vai para o celular. Tudo o que é só para testar fica fora.

### 5. O app começa vazio (pedido seu)

Antes, no build **debug**, o banco nascia com 2 propriedades e uns lançamentos (o `Semeador`, chamado no `onCreate` do Room). No release nunca teve.

- O `AgroSaldoDatabase.criar(context)` não semeia mais nada.
- Os dados de exemplo continuam existindo, mas só para os testes.
- Troquei os nomes por fictícios: **"Fazenda Santa Clara"**. Também nos `@Preview`. O nome real da fazenda não aparece mais em lugar nenhum do código.

### 6. Erro ao ler o banco não congela mais a tela

O Início, a lista de lançamentos, o Histórico e o Clima liam o banco com `combine(...).collect`. Se a leitura desse erro (banco travado por um instante, por exemplo), o Flow **morria**: a tela ficava parada até reabrir o app, ou o app caía.

Agora todos usam o `repetirAposErro { }` (`core/util/Erros.kt`):

1. a tela recebe `erro = "Não foi possível carregar…"` no UiState;
2. a leitura é refeita depois de 1 s, 2 s, 4 s… até 30 s;
3. quando volta, o `erro` some sozinho.

A lista de propriedades já fazia isso; agora as cinco telas fazem igual. **Mostrar** o erro bonitinho na tela é trabalho da R7 (componente `EstadoErro`).

👉 **Lição:** `.catch { }` num Flow de tela **encerra** o Flow. Para tela que observa o banco, o certo é **tentar de novo** (`retryWhen`).

## 3. O que testar no celular

Depois de **Limpar armazenamento**:

- [ ] O app abre no cadastro/login e, depois de entrar, mostra "Cadastre sua primeira propriedade" (vazio de verdade).
- [ ] Cadastre 2 propriedades e alguns lançamentos. O Início, a lista, o Histórico e "Sítios" mostram os **mesmos totais** de antes da R6 (a conta é a mesma).
- [ ] Troque a propriedade no Início e confira que Lançamentos, Clima e Histórico seguem a troca.
- [ ] Feche o app de vez e abra de novo: a propriedade escolhida continua escolhida.
- [ ] Ferramentas de teste do aviso (Ajustes do aviso, build debug): "Mostrar notificação de exemplo" e toque nela. O Clima abre na propriedade selecionada.
